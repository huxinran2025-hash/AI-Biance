## 审计概述

### 审计目标

本审计方法的**核心目标是通过系统化的问题发现机制，主动识别和定位BIANCE交易系统中的潜在问题、异常和风险**。与传统的"验证完成度"审计不同，本方法重点关注：

- **异常检测**：识别偏离正常状态的异常情况
- **问题发现**：主动发现潜在问题，而非验证功能是否完成
- **风险预警**：通过趋势分析和对比检测，提前发现系统恶化
- **数据一致性**：检测跨模块数据不一致和逻辑冲突
- **边界问题**：识别极端场景和边界条件下的问题

审计覆盖所有功能模块、AI服务、外部API、用户界面等各个方面，但**聚焦于发现异常而非验证正常**。

### 审计原则

1. **问题导向**：审计的核心是发现问题，而非验证完成度。绝大部分审计结果都是正常的，**重要的是找出那1%的异常**
2. **对比基准**：所有审计必须建立基准值（正常范围、历史平均值、预期值），通过对比发现异常
3. **趋势分析**：不仅关注当前状态，更要识别性能退化、错误率上升等趋势
4. **异常检测**：主动检测异常值、边界情况、不一致性，而非仅检查是否完整
5. **可追溯性**：所有审计结果必须可追溯，包含时间戳、上下文信息
6. **结构化问题报告**：问题必须按严重程度、影响范围、问题类型分类，便于优先级排序

### 基准值定义

为确保问题发现的有效性，每个审计模块必须定义基准值：

- **正常范围**：指标的正常值范围（如响应时间 < 1000ms，错误率 < 1%）
- **历史基准**：过去7天的平均值，用于趋势对比
- **阈值定义**：触发警告和错误的阈值
- **预期行为**：在特定场景下的预期行为模式

**示例：**
- AI服务响应时间基准：平均500ms，正常范围200-800ms，超过1500ms为异常
- 币安API成功率基准：正常 > 99%，低于95%为严重问题
- 提示词长度基准：正常范围1500-3000字符，异常短或过长需标记

### 审计频率

- **实时审计**：AI提示词、关键错误、模式切换（立即检测异常）
- **周期性审计**：每5分钟自动审计所有模块（检测趋势变化）
- **手动触发**：系统启动、关键操作后、问题排查时
- **完整审计**：每日生成完整审计报告（全面问题汇总）

## AI提示词审计（重点）

### 审计目标

通过对比检测、异常识别和数据一致性检查，**主动发现AI提示词生成过程中的问题**。重点关注：
- 三个模型之间提示词数据的不一致性
- 提示词内容与系统状态的冲突
- 数值异常（如负值、超出范围、计算错误）
- 场景不匹配（如PAUSED模式下仍允许开仓）
- 历史对比异常（同一场景下提示词突然变化）

### 三个AI模型

#### Model A: GPT-5 Momentum Strategist
- **角色**：趋势交易员，偏向多头
- **模型**：gemini-2.0-flash-001
- **系统提示词**：`你是一个纪律严格的趋势交易员，优先考虑做多顺势资产，但必须尊重风险约束、资金使用上限与新闻风险。任何建议都要包含进场方向、合理仓位、止损/止盈与无效条件。`

#### Model B: Gemini Contrarian Sentinel
- **角色**：防守型对冲交易员，偏向空头/减仓
- **模型**：gemini-2.0-flash-001
- **系统提示词**：`你是一名防守型对冲交易员，优先寻找做空或减仓机会，确保仓位符合风险与资金约束。任何新增仓位都必须严格审慎，并给出明确触发条件、止损、止盈。`

#### Model C: DeepSeek Multi-Asset Synthesizer
- **角色**：多资产组合再平衡
- **模型**：gemini-2.0-flash-001
- **系统提示词**：`你负责多资产组合再平衡。结合新闻、仓位表现、风险约束决定增减仓位。任何建议必须给出仓位比例、止损/止盈、失效条件。`

### 提示词问题发现机制

#### 1. 基础信息异常检测

**每次AI调用必须记录，并检测异常：**
- [ ] **异常检测**：模型ID是否有效（非model_A/model_B/model_C为异常）
- [ ] **异常检测**：时间戳是否合理（与上次调用间隔过短或过长）
- [ ] **异常检测**：会话ID是否连续（会话ID跳跃可能表示状态丢失）
- [ ] **异常检测**：Tick序号是否连续（序号跳跃或重复为异常）
- [ ] **异常检测**：系统模式是否与预期一致（NORMAL/PAUSED/REDUCE_ONLY等）
- [ ] **异常检测**：执行模式是否与配置一致（paper/shadow/live）

#### 2. 系统提示词异常检测

**对比检测，发现异常：**
- [ ] **不一致检测**：系统提示词是否与`MODEL_PROFILES`中的定义不一致（发现差异）
- [ ] **缺失检测**：系统提示词是否缺少JSON schema要求（应包含但未包含）
- [ ] **缺失检测**：系统提示词是否缺少角色定位说明（应包含但未包含）
- [ ] **异常检测**：系统提示词长度是否异常（过短或过长，超出正常范围）
- [ ] **对比检测**：同一模型的历史提示词是否发生变化（不应变化但变化了）

**审计点：**
```typescript
// 来源：backend/strategist/modelProfiles.ts
MODEL_PROFILES[modelId].systemPrompt
```

**基准值：**
- 系统提示词长度正常范围：100-500字符
- 系统提示词应与MODEL_PROFILES完全一致，任何差异都是问题

#### 3. 用户提示词审计

**每次调用必须完整记录用户提示词的所有部分：**

##### 3.1 角色说明部分
- [ ] 模型标签（label）是否正确
- [ ] 模型描述（description）是否完整
- [ ] 示例：`你是 GPT-5 Momentum Strategist（偏向趋势多头，利用强势新闻与价格动量寻找顺势做多机会，除非风险信号要求防守）。`

##### 3.2 账户状态部分 - 异常检测

**对比检测和数值异常检测：**
- [ ] **数值异常检测**：净值（equityNowUsd）是否为负值或零（异常）
- [ ] **数值异常检测**：峰值（equityPeakUsd）是否小于当前净值（逻辑错误）
- [ ] **数值异常检测**：可用现金（availableCapital）是否为负值（异常）
- [ ] **数值异常检测**：当前总敞口（exposureNowUsd）是否为负值（异常）
- [ ] **数值异常检测**：上限（capUsd）是否为零或负值（配置错误）
- [ ] **计算异常检测**：敞口百分比（exposurePct）计算是否正确（exposureNowUsd / capUsd * 100）
- [ ] **范围异常检测**：敞口百分比是否超过100%（严重问题）
- [ ] **不一致检测**：系统模式（state.systemStatus.mode）是否与提示词中描述的模式一致
- [ ] **缺失检测**：触发原因（reason）是否缺失（应包含但未包含）
- [ ] **不一致检测**：风控冷静模式状态（riskState.cooldownActive）是否与提示词描述一致
- [ ] **数值异常检测**：风控指标是否在合理范围：
  - 现金占比（cashRatio）是否在0-100%之间
  - 保证金占用（marginUsage）是否在0-100%之间
  - 账户杠杆（accountLeverage）是否在合理范围（如0-10x）
  - 最大回撤（drawdownPct）是否为负值或超过100%（异常）
- [ ] **对比检测**：三个模型的账户状态数据是否一致（应一致但不一致为异常）

**审计示例（发现问题）：**
```
## 账户状态 - 发现异常
- 净值: $10,000.00（峰值 $10,500.00）✅
- 可用现金: $8,000.00 ✅
- 当前总敞口: $2,000.00 / 上限 $3,000.00 (66.7%) ✅
- ⚠️ 异常：敞口百分比计算错误，实际应为66.7%但提示词显示为70%
- ⚠️ 异常：系统模式显示为NORMAL，但风控冷静模式为"是"，存在冲突
- ⚠️ 异常：最大回撤显示为-5.2%（负值，应为正数）
```

##### 3.3 持仓概览部分 - 异常检测

- [ ] **不一致检测**：提示词中的持仓数量是否与实际系统持仓数量不一致
- [ ] **格式异常检测**：持仓格式是否错误（符号格式、方向值、数值格式等）
- [ ] **逻辑异常检测**：持仓是否按时间排序（无序为异常）
- [ ] **不一致检测**：空持仓时是否错误显示持仓信息（或相反，有持仓时显示"暂无持仓"）
- [ ] **数值异常检测**：持仓规模是否为负值或零（异常）
- [ ] **计算异常检测**：持仓盈亏计算是否正确
- [ ] **对比检测**：三个模型的持仓列表是否一致（应一致）

##### 3.4 新闻与警报部分 - 异常检测

**不一致检测和缺失检测：**
- [ ] **不一致检测**：提示词中的新闻列表是否与实际系统新闻列表不一致
- [ ] **不一致检测**：提示词中的外部警报是否与实际系统警报不一致
- [ ] **不一致检测**：提示词中的黑名单交易对是否与实际黑名单不一致
- [ ] **不一致检测**：提示词中的模型分歧信号是否与实际信号不一致
- [ ] **缺失检测**：存在关键新闻时，提示词是否遗漏（应包含但未包含）
- [ ] **过度包含检测**：不存在关键新闻时，提示词是否错误包含新闻（不应包含但包含了）
- [ ] **对比检测**：三个模型的新闻与警报数据是否一致（应一致）
- [ ] **严重程度异常**：新闻严重程度标记是否正确（critical/normal标记错误）

**审计示例（发现问题）：**
```
## 新闻与警报 - 发现异常
- ⚠️ 异常：系统中有3条关键新闻，但提示词中只包含2条
- ⚠️ 异常：黑名单实际为[BTCUSDT, ETHUSDT, SOLUSDT]，但提示词中缺少SOLUSDT
- ⚠️ 异常：model_A的新闻列表与model_B不一致（应一致）
```

##### 3.5 技术分析部分 - 异常检测

**当存在K线数据时（klineSnapshot存在），检测异常：**

- [ ] **数值异常检测**：MA20和MA50的值是否合理（不应为零或负值）
- [ ] **逻辑异常检测**：趋势判断与MA关系是否一致（如MA20>MA50但判断为下跌趋势）
- [ ] **范围异常检测**：RSI值是否在0-100范围内（超出为异常）
- [ ] **不一致检测**：RSI超买/超卖判断是否与RSI值一致（如RSI>70但判断为超卖）
- [ ] **数值异常检测**：MACD值是否合理（异常大或异常小）
- [ ] **数值异常检测**：布林带上下轨是否合理（上轨应>中轨>下轨）
- [ ] **逻辑异常检测**：当前价格相对布林带位置判断是否正确
- [ ] **不一致检测**：波动率判断是否与实际数据一致
- [ ] **数值异常检测**：支撑位/阻力位是否合理（不应为零或负值）
- [ ] **对比检测**：三个模型的技术分析数据是否一致（应一致）
- [ ] **缺失检测**：应包含技术分析但未包含（异常）

**当不存在K线数据时，检测异常：**
- [ ] **过度包含检测**：不应包含技术分析但包含了（严重错误）
- [ ] **不一致检测**：hasKlineSnapshot为false但提示词包含技术分析

##### 3.6 可交易标的部分 - 异常检测

- [ ] **不一致检测**：提示词中的交易对列表是否与实际allowedPairs不一致
- [ ] **格式异常检测**：交易对格式是否正确（应为大写，如BTCUSDT而非btcusdt）
- [ ] **计算异常检测**：剩余可用敞口（remainingExposureUsd）计算是否正确（capUsd - exposureNowUsd）
- [ ] **数值异常检测**：剩余可用敞口是否为负值（超过上限为严重问题）
- [ ] **不一致检测**：是否允许新开仓（allowNewEntries）的判断是否与实际系统状态一致
  - PAUSED模式下应禁止开仓，但提示词允许开仓为异常
  - REDUCE_ONLY模式下应禁止开仓，但提示词允许开仓为异常
  - 风控冷静模式下应禁止开仓，但提示词允许开仓为异常
  - 剩余可用敞口为0或负值时应禁止开仓，但提示词允许开仓为严重异常
- [ ] **缺失检测**：禁止开仓时是否缺少明确提示（应包含但未包含）
- [ ] **对比检测**：三个模型的可交易标的数据是否一致（应一致）

**审计示例（发现问题）：**
```
## 可交易标的 - 发现严重异常
- ⚠️ 严重异常：系统模式为PAUSED，但提示词显示"当前允许在风险范围内开仓"
- ⚠️ 异常：剩余可用敞口计算错误，实际为-$500.00（已超限），但提示词显示为$1,000.00
- ⚠️ 异常：实际允许交易对为[BTCUSDT, ETHUSDT]，但提示词包含SOLUSDT（不在列表中）
```

##### 3.7 输出要求部分 - 异常检测

- [ ] **缺失检测**：是否缺少JSON格式要求（应包含但未包含）
- [ ] **缺失检测**：是否缺少action枚举值（应包含但未包含）
- [ ] **不一致检测**：禁止开仓时是否缺少约束说明（应强调但未强调）
- [ ] **缺失检测**：是否缺少notionalUsd上限约束（应包含但未包含）
- [ ] **缺失检测**：是否缺少止损/止盈/无效条件要求（应包含但未包含）
- [ ] **缺失检测**：是否缺少confidence范围说明（应包含但未包含）
- [ ] **缺失检测**：是否缺少reasoning要求（应包含但未包含）
- [ ] **条件不一致检测**：有K线数据时是否缺少技术分析说明要求（应包含但未包含）
- [ ] **过度包含检测**：无K线数据时是否错误包含技术分析说明要求（不应包含但包含了）
- [ ] **不一致检测**：禁止开仓时的约束说明是否与系统状态一致（如PAUSED模式应明确禁止buy_to_enter和sell_to_enter）

### 不同场景下的问题发现

#### 场景1：正常模式（NORMAL）+ 无持仓 + 有K线数据
**问题发现重点：**
- [ ] **异常检测**：系统模式是否错误显示为非NORMAL（应为NORMAL但显示为其他）
- [ ] **不一致检测**：触发原因是否与系统实际状态不一致
- [ ] **不一致检测**：风控冷静模式是否错误显示为"是"（应为"否"）
- [ ] **不一致检测**：是否错误禁止开仓（正常模式下应允许开仓）
- [ ] **缺失检测**：技术分析部分是否缺失（应包含但未包含）
- [ ] **不一致检测**：持仓概览是否错误显示持仓（应为"暂无持仓"）

#### 场景2：正常模式（NORMAL）+ 有持仓 + 无K线数据
**问题发现重点：**
- [ ] **不一致检测**：持仓概览是否与实际持仓不一致（数量、内容不一致）
- [ ] **过度包含检测**：技术分析部分是否错误包含（不应包含但包含了）
- [ ] **过度包含检测**：输出要求中是否错误包含技术分析说明要求（不应包含但包含了）

#### 场景3：暂停模式（PAUSED）
**问题发现重点：**
- [ ] **不一致检测**：系统模式是否错误显示为非PAUSED（应为PAUSED但显示为其他）
- [ ] **缺失检测**：触发原因是否缺失（应包含但未包含）
- [ ] **严重异常**：是否错误允许开仓（PAUSED模式下应禁止开仓）
- [ ] **缺失检测**：输出要求中是否缺少禁止buy_to_enter和sell_to_enter的明确说明（应强调但未强调）

#### 场景4：减仓模式（REDUCE_ONLY）
**问题发现重点：**
- [ ] **不一致检测**：系统模式是否错误显示为非REDUCE_ONLY（应为REDUCE_ONLY但显示为其他）
- [ ] **缺失检测**：触发原因是否缺失（应包含但未包含）
- [ ] **严重异常**：是否错误允许开仓（REDUCE_ONLY模式下应禁止开仓）
- [ ] **缺失检测**：输出要求中是否缺少"只能持有或减仓"的明确说明（应强调但未强调）

#### 场景5：风控冷静模式激活
**问题发现重点：**
- [ ] **不一致检测**：风控冷静模式是否错误显示为"否"（应为"是"）
- [ ] **缺失检测**：冷静原因（cooldownReason）是否缺失（应包含但未包含）
- [ ] **严重异常**：是否错误允许开仓（冷静模式下应禁止开仓）
- [ ] **缺失检测**：账户状态部分是否缺少冷静模式信息（应包含但未包含）

#### 场景6：资金使用上限接近/超过
**问题发现重点：**

## 问题发现机制

### 1. 对比基准法

通过定义正常范围、历史基准和阈值，对比当前值发现异常。

**实施步骤：**
1. **定义基准值**：为每个指标定义正常范围、历史平均值、警告阈值、错误阈值
2. **实时对比**：将当前值与基准值对比
3. **异常标记**：超出阈值时标记为异常
4. **趋势分析**：对比历史平均值，发现恶化趋势

**示例：**
- AI响应时间：正常<800ms，历史平均500ms，超过1500ms为异常，超过1200ms为警告
- 错误率：正常<1%，历史平均0.5%，超过5%为严重异常，超过3%为警告

### 2. 趋势分析法

通过分析历史数据趋势，发现逐渐恶化的问题。

**实施步骤：**
1. **收集历史数据**：保存过去7-30天的指标数据
2. **计算趋势**：计算平均值、中位数、标准差
3. **识别趋势**：判断是否呈上升/下降趋势（连续3次检查）
4. **预警标记**：趋势恶化时标记为警告

**趋势类型：**
- **上升趋势**：错误率、延迟、内存使用等（越差越好）
- **下降趋势**：成功率、响应质量等（越差越差）
- **波动异常**：标准差突然增大（不稳定）

### 3. 不一致性检查

通过对比不同数据源或模块，发现数据不一致。

**检查类型：**
1. **跨模块不一致**：前端显示 vs 后端数据
2. **跨模型不一致**：三个AI模型的提示词数据
3. **状态不一致**：提示词内容 vs 实际系统状态
4. **计算不一致**：不同计算方式得到的结果
5. **时间不一致**：不同时间点的数据应该一致但不一致

**实施步骤：**
1. **定义一致性规则**：哪些数据应该一致
2. **实时对比**：对比不同数据源
3. **差异计算**：计算差异百分比
4. **异常标记**：差异超过阈值时标记为异常

### 4. 异常值检测

识别超出正常范围的异常值。

**检测方法：**
1. **范围检测**：是否在合理范围内（如百分比在0-100%）
2. **统计检测**：是否超出3倍标准差（统计异常）
3. **逻辑检测**：是否符合业务逻辑（如峰值应>=当前值）
4. **边界检测**：是否接近或超过边界值（如敞口接近100%）

### 5. 异常模式识别

识别重复出现的异常模式。

**模式类型：**
1. **时间模式**：特定时间段频繁出现异常
2. **类型模式**：特定类型的错误频繁出现
3. **组合模式**：多个异常同时出现
4. **序列模式**：异常按特定序列出现

**实施步骤：**
1. **模式记录**：记录所有异常及其上下文
2. **模式分析**：分析异常的时间、类型、组合关系
3. **模式识别**：识别重复出现的模式
4. **预警**：相同模式再次出现时预警

### 6. 边界条件测试

主动测试极端场景和边界条件。

**测试场景：**
1. **数值边界**：最大值、最小值、零值、负值
2. **状态边界**：模式切换、状态转换
3. **资源边界**：内存上限、并发上限、速率上限
4. **时间边界**：超时、过期、时间同步

**实施步骤：**
1. **场景定义**：定义所有边界场景
2. **主动测试**：定期或在特定条件下触发边界测试
3. **异常记录**：记录边界条件下的异常行为
4. **修复验证**：验证修复后边界条件是否正常

## 问题分类体系

### 严重程度分级

#### CRITICAL（严重）
- **定义**：可能导致系统崩溃、资金损失、数据损坏的严重问题
- **特征**：
  - 资金安全风险
  - 系统无法运行
  - 数据丢失或损坏
  - 风控机制失效
- **响应时间**：立即处理（< 1小时）
- **示例**：
  - 资金使用上限被突破
  - 风控限制被绕过
  - Live模式执行了错误订单
  - 数据损坏或丢失

#### ERROR（错误）
- **定义**：影响功能正常使用，但不会立即导致严重损失的问题
- **特征**：
  - 功能异常
  - 数据不一致
  - 性能严重下降
  - 错误率异常高
- **响应时间**：24小时内处理
- **示例**：
  - API连接失败
  - 数据同步不一致
  - 响应时间超过3秒
  - 错误率超过5%

#### WARNING（警告）
- **定义**：潜在问题，可能发展为错误，需要关注
- **特征**：
  - 性能下降趋势
  - 异常值接近阈值
  - 数据轻微不一致
  - 错误率上升趋势
- **响应时间**：3天内处理
- **示例**：
  - 响应时间超过历史基准150%
  - 错误率连续3次上升
  - 数据同步延迟增加
  - 内存使用接近上限

#### NORMAL（正常）
- **定义**：系统运行正常，无异常
- **特征**：
  - 所有指标在正常范围
  - 无异常模式
  - 数据一致性良好
- **响应时间**：无需处理

### 影响范围分类

#### 系统级
- **定义**：影响整个系统运行
- **影响**：所有用户、所有功能
- **示例**：系统模式切换失败、数据库连接失败

#### 模块级
- **定义**：影响特定模块
- **影响**：模块内所有功能
- **示例**：AI服务异常、币安API异常

#### 功能级
- **定义**：影响特定功能
- **影响**：单个功能无法使用
- **示例**：订单执行失败、账户同步失败

### 问题类型分类

#### 数据异常
- **定义**：数据值异常、格式错误、计算错误
- **子类型**：
  - 数值异常（负值、超出范围）
  - 格式异常（时间格式、货币格式）
  - 计算异常（百分比计算错误）
- **示例**：敞口百分比超过100%、负的净值

#### 逻辑错误
- **定义**：业务逻辑错误、判断错误
- **子类型**：
  - 状态判断错误
  - 条件判断错误
  - 流程逻辑错误
- **示例**：PAUSED模式下允许开仓、趋势判断与数据不一致

#### 性能问题
- **定义**：响应时间慢、资源占用高
- **子类型**：
  - 延迟过高
  - 内存泄漏
  - CPU占用过高
  - 网络请求过多
- **示例**：API响应时间超过3秒、内存使用超过500MB

#### 配置错误
- **定义**：配置值错误、配置缺失
- **子类型**：
  - 配置值错误
  - 配置缺失
  - 配置冲突
- **示例**：API密钥无效、阈值配置错误

#### 不一致性
- **定义**：数据不一致、状态不一致
- **子类型**：
  - 跨模块不一致
  - 跨模型不一致
  - 状态不一致
  - 时间不一致
- **示例**：前端显示与后端数据不一致、三个模型提示词不一致

#### 缺失问题
- **定义**：应包含但未包含、应执行但未执行
- **子类型**：
  - 数据缺失
  - 功能缺失
  - 日志缺失
- **示例**：关键新闻缺失、技术分析部分缺失

#### 过度包含
- **定义**：不应包含但包含了、不应执行但执行了
- **子类型**：
  - 数据过度包含
  - 功能过度执行
- **示例**：无K线数据时包含技术分析、PAUSED模式下执行开仓

### 紧急程度分类

#### 立即修复（P0）
- **定义**：CRITICAL级别问题，必须立即处理
- **响应时间**：< 1小时
- **处理方式**：紧急修复、系统暂停

#### 计划修复（P1）
- **定义**：ERROR级别问题，需要尽快处理
- **响应时间**：24小时内
- **处理方式**：制定修复计划，优先处理

#### 监控观察（P2）
- **定义**：WARNING级别问题，需要持续监控
- **响应时间**：3天内评估
- **处理方式**：持续监控，评估是否需要修复

#### 定期优化（P3）
- **定义**：性能优化、代码重构类问题
- **响应时间**：1周内评估
- **处理方式**：纳入优化计划

## 注意事项

1. **审计的第一步必须是全面读取工程代码库**。只有在充分理解代码后，才能发现真实的问题。不能基于假设或模板进行审计。

2. **所有问题必须基于实际代码**。每个发现的问题都必须：
   - 有明确的代码位置（文件路径、行号）
   - 有代码片段作为证据
   - 有具体的问题说明
   - 不能是假设或推测

3. **审计的核心是发现问题，而非验证完成度**。绝大部分审计结果都是正常的，重要的是找出那1%的异常。

4. **代码审计优先于运行时审计**。先通过代码审计发现潜在问题，再通过运行时审计验证问题是否存在。

5. **AI提示词审计是每次AI调用必须执行的，不能遗漏**。重点关注异常和不一致，而非验证是否完整。

6. **所有审计结果必须包含时间戳和上下文信息**，便于问题追溯和分析。

7. **发现问题必须立即记录，不能延迟**。按严重程度分类，优先处理CRITICAL和ERROR级别问题。

8. **基准值必须定期更新**。问题解决后，历史基准值需要更新，以反映系统的正常状态。

9. **趋势分析是关键**。不仅要关注当前状态，更要识别性能退化、错误率上升等趋势。

10. **审计方法需要随着系统发展不断更新**。新发现的问题类型需要纳入审计范围。

11. **新功能添加时必须同步更新审计清单**，并定义新功能的基准值和异常阈值。
